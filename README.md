# Multi-Agent RAG over PDFs

A retrieval-augmented Q&A system over a local folder of PDFs, orchestrated by
plain Python (asyncio) — no agent framework. Four agents (Router, Retriever,
Synthesizer, Critic) communicate only through a shared `State` object.

## Architecture

```
query -> Router/Planner Agent -> [Retriever Agent] -> Synthesis Agent -> [Critic Agent]
                                                                              |
                                              (unsupported? retry once) <----/
```

- **Router/Planner Agent** (`src/agents/router.py`) — classifies the query as
  `NO_RETRIEVAL`, `SINGLE_RETRIEVAL`, or `MULTI_RETRIEVAL` and, for the
  latter two, produces the search sub-queries to run.
- **Retriever Agent** (`src/agents/retriever.py`) — embeds each sub-query
  (Gemini, `task_type=RETRIEVAL_QUERY`), searches Chroma, merges/dedupes
  results across sub-queries, keeps the top `MAX_CONTEXT_CHUNKS`.
- **Synthesis/Answer Agent** (`src/agents/synthesizer.py`) — generates a
  cited, context-grounded answer with Gemini; falls back to a clearly-labeled
  general-knowledge answer when there's no retrieved context.
- **Critique/Verifier Agent** (`src/agents/critic.py`) — checks the answer's
  claims against the retrieved chunks, returning `SUPPORTED` /
  `PARTIALLY_SUPPORTED` / `UNSUPPORTED` + an explanation. If not `SUPPORTED`,
  the Orchestrator retries retrieval+synthesis once using the critic's
  suggested follow-up query (`config.MAX_CRITIC_RETRIES`). Skip with
  `--no-critic`.

All agents implement `async def run(state: State) -> State` and only touch
`State` (`src/agents/state.py`) — never each other or module-level globals.
`src/orchestrator.py` is the only place that knows the agent sequence.

## Folder structure

```
data/                  source PDFs (input)
storage/               persisted Chroma DB (generated by ingestion)
src/
  config.py            all tunables: models, chunk size, top_k, paths
  llm/gemini_client.py thin async wrapper: embed_texts(), generate()
  ingestion/
    loader.py           PDF -> per-page text (pypdf)
    chunker.py           text -> overlapping chunks
    ingest.py             load -> chunk -> embed -> store; CLI entrypoint
  vectorstore/chroma_store.py  Chroma add()/query() wrapper
  agents/
    state.py            shared State + AgentEvent (trace) + Critique
    router.py / retriever.py / synthesizer.py / critic.py
  orchestrator.py       sequences agents over State
cli.py                  entry point
requirements.txt
.env.example
```

## Design decisions

- **Vector store: Chroma**, not FAISS. Chroma persists to a local directory
  and stores embeddings + document text + metadata (source file, page,
  chunk index) together, so retrieval results come back citation-ready with
  no separate id → text/metadata lookup to maintain. FAISS is a faster raw
  index but ships no persistence or metadata layer — you build that
  yourself. For a local, low-hundreds-of-thousands-of-chunks PDF corpus,
  Chroma's simplicity wins; FAISS would be worth it at much larger scale or
  if you needed fine-grained index tuning (IVF/HNSW/PQ). The vector store is
  behind a small wrapper (`ChromaStore`), so swapping is a contained change.
- **Chunking**: ~1000 characters with ~200 character overlap, split on
  paragraph then sentence boundaries (never mid-sentence unless a single
  sentence exceeds the chunk size). Chunking is per-page rather than across
  page boundaries, trading a small amount of cross-page continuity for exact
  `source_file` + `page_number` citations on every chunk.
- **Embeddings**: `gemini-embedding-001`, requested at 768 dimensions, with
  asymmetric encoding — `RETRIEVAL_DOCUMENT` at ingest time,
  `RETRIEVAL_QUERY` at query time — which improves retrieval over using the
  same encoding for both. Embeddings are L2-normalized client-side since
  the model only auto-normalizes at its native (3072) dimensionality.
- **Generation model**: the spec asked for `gemini-2.5-flash`, but this API
  key gets `404 NOT_FOUND` on it ("no longer available to new users"); the
  API's own error pointed to `gemini-3.6-flash`, so `config.py` uses that.
  Change `GENERATION_MODEL`/`ROUTER_MODEL` in `src/config.py` if your key
  has access to a different model.
- **Bounded retry, not a loop**: the Critic can trigger at most
  `MAX_CRITIC_RETRIES` (default 1) extra retrieval+synthesis passes, so a
  stubbornly unsupported answer still returns (with an honest verdict)
  instead of looping.

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # then fill in GEMINI_API_KEY
```

## Usage

```bash
# 1. Ingest PDFs from ./data into the local Chroma store
python -m src.ingestion.ingest --reset

# 2. Ask questions
python cli.py "What are the check-in guidelines?"
python cli.py --no-critic "What are the check-in guidelines?"   # skip verification, faster
python cli.py                                                    # interactive REPL
```

Each answer prints, in order: which agents ran (with their inputs/outputs),
the retrieved chunks (source file, page, similarity score, preview), the
critic's verdict, and the final answer.

## Notes / limitations

- PDF text extraction (`pypdf`) is text-layer only — scanned/image-only PDFs
  need OCR first (not included).
- Re-running ingestion without `--reset` appends/upserts; chunk IDs are
  deterministic (`file::page::chunk_index`), so re-ingesting the same PDF
  overwrites its old chunks rather than duplicating them.
- The Router and Critic use `response_mime_type="application/json"`
  structured output; both have a safe fallback (default to
  `SINGLE_RETRIEVAL`, or `PARTIALLY_SUPPORTED`) if parsing ever fails.
